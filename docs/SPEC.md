# SQL探偵：ログの死角 仕様書（SPEC）

作成日: 2026-11-16 / 更新日: 2026-11-16 / ステータス: **MVP確定（実装済み）**

## 概要

ランダム生成ログDBで犯人を当てる推理ゲーム。

毎回ランダム生成される注文／ログイン／送金ログのDBから、JOINと集計で容疑者を絞り、犯人を1人告発する。不完全な情報を読むことがそのまま推理になる。

## 共通前提

- プレイヤーが書けるのは原則 `SELECT` のみ。DBは読み取り専用接続で開く
- 実行制限: 1クエリ 100ms / 取得上限 100行
- 1プレイ完結型。セーブはラン単位のみ
- オンライン対戦・ランキングはMVP外

## 数値仕様

| 項目 | 値 | 備考 |
|---|---|---|
| 1事件のプレイ時間 | 5〜10分 | |
| クエリ実行 | 8回まで | 捜査コスト |
| 1クエリの実行時間上限 | 100ms | 超過は中断し、コストは消費しない |
| 取得上限 | 100行 | 超過分は切り捨てて表示 |
| LIMITなし全件取得 | コスト2倍 | 2行以上返した場合のみ。1行なら1 |
| 告発 | 無料 | コストを消費しない |

### コストの数え方

コストは**実行前の見積りではなく結果で決まる**。

- `LIMIT` 句があり、かつ2行以上返した → コスト1
- `LIMIT` 句がなく、かつ2行以上返した → コスト2
- 返った行数が0〜1行 → コスト1（集計クエリを不当に重くしない）

`LIMIT` の有無は文字列リテラル内を無視して判定する（`SELECT 'limit'` は該当しない）。

### コストを使い切ったとき

コストが0になった時点では**まだ敗北しない**。告発は無料でいつでもできるため、
最後の1回を使い切った状態からでも告発できる（スコアは0になる）。
コスト0でさらに捜査しようとした時点で「使い切った」敗北が確定する。

## テーブル（固定4つ、列構成は固定・データだけランダム）

| テーブル | 用途 | 列 |
|---|---|---|
| users | 容疑者マスタ | id, name, department, joined_at, is_admin |
| orders | 注文ログ | id, user_id, amount, created_at, status |
| logins | ログインログ | id, user_id, logged_in_at, ip, success |
| transfers | 送金ログ | id, from_user_id, to_user_id, amount, created_at, memo |

テーブル構成までランダムにすると推理が運ゲーになるため、構成は固定する。

## 生成ルール（最重要制約）

- 犯人は「条件を満たすのが1人だけ」になるようデータを逆算生成する
- **解が複数ある事件は絶対に出さない**。生成後に検証クエリで一意性を確認し、満たさなければ再生成する
- 生成はシードで決定的。同じシードからは常に同じ事件が出る

### 事件テンプレート

各テンプレートは「依頼文」と「一意性を検証する述語SQL」を持つ。
述語SQLが返す `user_id` がちょうど1人＝犯人のときだけ、その事件を採用する。

| key | 依頼 | 決め手 |
|---|---|---|
| midnight_transfer | 深夜0〜5時に50万円以上の送金をしたのは誰か | 時刻と金額の複合 |
| login_bruteforce | 同一IPから3回以上ログインに失敗したのは誰か | user_id × ip のグループ集計 |
| bulk_orders | 同じ日に10万円以上の注文を3件以上出したのは誰か | user_id × 日付のグループ集計 |
| admin_impersonation | 非管理者が管理者へ30万円以上を送金したのは誰か | users への2回JOIN |

各テンプレートには**ニアミス**（条件を1つだけ外す容疑者）を意図的に混ぜる。
これにより「絞り込みの条件を1つ落とすと複数人出る」状態になり、推理が成立する。

## 勝敗条件

- 勝利: 告発が当たる（スコア＝残りクエリ数）
- 敗北: 告発を外す、またはコスト0で捜査を続けようとする
- 告発はID・氏名のどちらでも受け付ける（空白は無視）

## 実装

- 言語: Python 3.11+
- DB: SQLite（`mode=ro` + `PRAGMA query_only` の二重防御）
- UI: CLI（`sql-detective play` / `sql-detective verify`）
- 依存: 標準ライブラリのみ。テストは pytest

### モジュール構成

| ファイル | 役割 | Issue |
|---|---|---|
| `sql_detective/db.py` | 読み取り専用実行基盤・SELECT限定・時間/行数上限・コスト計測 | #2 |
| `sql_detective/case.py` | 事件生成（逆算生成＋一意性検証） | #4 |
| `sql_detective/game.py` | コアループ（捜査→告発→判定・スコア） | #3 |
| `sql_detective/cli.py` | CLI UI と `verify` サブコマンド | #5 |

## デバッグモード

`python -m sql_detective.cli debug [--seed 整数]` で通常プレイとは別に起動する。
シード・生成再試行回数・事件種別・進行状態・捜査履歴の確認、犯人と検証SQLの表示、
現在のDBの一意性検証、残りコストの変更、同一事件の初期化ができる。
勝敗後も初期化して再試行できる。詳細な操作はREADMEを参照する。

デバッグコマンドは通常の `play` では有効にならない。一意性検証はコストを消費せず、
犯人情報を表示する操作はネタバレと明示する。SQLの読み取り専用・時間・行数制限は維持する。
